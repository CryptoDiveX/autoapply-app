# Lazy employer careers boards

1. Treat a careers heading plus an initially blank iframe as unresolved loading, not zero openings or a broken application route. Body text length and document readiness do not prove board readiness.
2. After a bounded same-target read-only wait, inspect actual iframe attributes and the page's observed hiring-widget scripts. An employer can load an Ashby embed script first and populate its iframe later. An exact `/tenant/embed` script source is JavaScript, not the native board document. Read its observed `window.__ashbyBaseJobBoardUrl` configuration and follow that exact published base URL if the wrapper never produces its iframe; do not navigate the script itself expecting role cards, guess a tenant route or classify its source text as an empty inventory.
3. Follow only the exact employer-published iframe URL after it appears. Preserve the official page, exact script URL, observed iframe URL and the settled native inventory together. Do not construct a tenant slug, mutate iframe attributes or use customer-contact widgets as application routes.
4. Require the actual native board's settled role count and cards. A careers wrapper without cards does not establish employer-wide closure; an exact current zero-role board establishes its current inventory only. Search mirrors can retain obsolete implementation or customer-success roles after that board changes.
5. Before fetching an advertised role from the board, repeat the exact posting-ID and employer-alias lifecycle gate. Discovery of a current board does not clear geography, specialist, country, consent, document or prior-attempt restrictions.
6. If a public HTML request fails after a successful board readback, preserve that failure and recover only the read-only page source or iframe evidence. Never repeat candidate actions or a completed inventory script just to repair a later independent fetch.
