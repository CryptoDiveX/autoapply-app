# Email bounce suppression

1. Use `~/Hermes/job-applications/outreach-database/email-suppression.json` as the persistent blocked-recipient register for VB Jobs applications and recruiter follow-ups. Preserve earlier exclusions and recorded temporary failures until reviewed. Never automatically retry, repair spelling or guess an alternate address. Only Vasya can release an exact blocked address.
2. Immediately inside every actual email sending path, call `~/.hermes/profiles/vb-jobs/scripts/email_recipient_guard.py` with all exact To, CC and BCC recipients using subprocess.run(..., check=True), and save the receipt. Missing/malformed registry or active `~/Hermes/job-applications/daily-100-applications/EMAIL_AUDIT_HOLD.json` must fail closed. The shared tick_common.gog direct-send helper calls it, but alternate helpers, drafts and direct APIs need their own explicit guard call. Do not claim universal interception or that already-imported functions reload automatically.
3. Include Trash and Spam with in:anywhere when finding delivery failures. Parse actual failed recipients from structured delivery-status or explicit provider failure sentences, never all addresses from quoted original messages. A postmaster sender alone is not failure evidence. Preserve NDR ID, action, status, exact recipient and original-message correlation. Delay does not prove a nonexistent mailbox: hold it from fresh outreach without inventing a permanent diagnosis.
4. Update the canonical register under a local exclusive lock, merge existing addresses, retain evidence and synchronize campaign no-retry lists before further email. Bounced applications earn no credit; a follow-up-only bounce does not invalidate a separate successful ATS application. Inspect existing failed lifecycle and exact Teal record before writing corrections, never replay sending or tracker transitions simply to refresh the audit.
5. Test every blocked address case-insensitively, a display-name address, mixed To/CC/BCC, active hold, missing registry and a nonsending allowed control. Exercise the actual sender helper and prove prohibited recipients stop before the mail CLI. Tests must never send, and must distinguish the active-hold test from recipient suppression so the hold does not mask a broken BCC parser.
10. Extract original RFC Message-ID and NDR In-Reply-To from the exact Gmail message payload headers, not only gog's convenience headers dictionary, which can be populated while omitting both fields. Preserve the exact correlation and decoded delivery-status ancestry. Print only whitelisted hiring headers, relevant candidate/recruiter body and delivery-status text; never dump text/rfc822-headers parts or authentication/signing headers during NDR inspection. A missing convenience field is a read-only schema recovery, not permission to resend.

8. Keep bounce searches paginated and distinguish historical personal-address failures from current campaign failures. A register can preserve both under VB Jobs scope, but do not report all historical failures as newly bounced job applications. Exclude ordinary notices from postmaster-named services rather than blocking their contacts.
11. Validate each guard receipt against its actual schema: `email_recipient_guard.py` returns `allowed: true` and the exact recipient list, while `approved_resume_guard.py` returns `ok: true` and file fingerprints. Do not assume both guards use `ok`. A post-send verifier key mismatch requires only read-only schema recovery and unfinished logging, never another email, attachment upload or tracker transition.

9. Omit absent CC/BCC CLI arguments rather than passing empty strings to a sender that forwards every argument to the recipient guard. Keep explicit empty recipient arrays in the retained intent and verify actual Sent headers contain no CC/BCC. Never weaken the guard to accept empty recipient tokens. If a wrapper rejects those tokens before the mail CLI executes, preserve the exact failure, verify no provider result and an empty exact Sent search, then recover only the demonstrably unsent stage under a new immutable continuation intent with fresh immediate recipient and attachment guards. An uncertain provider call still prohibits automatic replay.
