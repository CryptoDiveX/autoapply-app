# Remote-board to Workable verification

1. Disambiguate same-name employers using the official domain, ATS tenant, product and business type before applying or finding contacts. Recruiter search results can mix a design agency with unrelated sales-data software.
2. Inspect the live official role and application form before copywriting. Workable job-card anchors can have no inner text; locate the matching title's enclosing `li[data-ui=job]` or `li[data-ui=job-opening]` and read its observed anchor href instead of concluding no apply route exists. The visible h3 can be a non-clickable sibling under a full-card overlay anchor, so clicking the title may leave the board unchanged. Follow only that exact observed href and recover the read-only native role stage, not an application action. A Jobs by Workable Apply modal that shows only Cancel and disabled Submit is not a hydrated candidate form; prefer the current employer-linked native board before declaring the actual route blocked.
3. Reuse only a byte-identical approved PDF in emergency approved-document mode. Supply role-specific Sonnet cover text through the native cover field when offered.
4. After native resume upload settles, fill and read every question/value pair, including exact monthly salary units and current Batumi location. Treat a plain custom Location question separately from an autocomplete with hidden normalized fields.
5. Enable CDP Network observation before a single native Submit click. Require successful submit response, such as HTTP 201 from the actual Workable apply request, plus live successful-submission text with no remaining form. Upload success and a success-looking URL alone are insufficient.
6. Normalize Teal Date Applied to UTC second precision before equality checks because Teal drops fractional seconds. Read the saved status relationship, date, original URL, salary unit and notes back after every write. Do not use a literal APPLIED note heading as a status assertion: a readable APPLICATION section can describe a verified submission correctly, while an APPLIED heading can coexist with an actual Applying record. For exact-body auditing, parse HTML paragraphs, decode entities and normalize transport whitespace in the comparison view only; preserve original submitted text and raw note evidence. If an assertion fails, inspect the exact mismatched field before changing records or weakening the check.
7. Open the exact Teal record in a background target and select Notes. If plain-text API notes render as a wall, rewrite with actual Enter key events in the rich editor and verify separate block paragraphs and newline-separated bullets, then read the exact record again. Preserve Applied status during notes-only repairs.
8. When Gmail bounce search returns a thread whose top summary is the sent application, inspect individual messages. A delivery failure can be threaded under that sent subject. Save the exact failure message, archive the affected target with applied_at null, mark the event DELIVERY FAILED and non-counted, and never retry that address.
9. Keep ATS submission status separate from recruiter outreach status. Match a bounce to the exact sent message and event purpose before changing the application count. A later follow-up email failure does not invalidate an independently verified ATS application, but it must change that outreach event to failed. Preserve the native submit timestamp as Date Applied; store the follow-up's provider timestamp only on its outreach event.
10. Close only owned completed or dead targets after saving evidence. Re-enumerate after a bounded delay because close acknowledgements can precede target disappearance, and sibling lanes may restart the shared browser and invalidate old IDs.

## Recruitee native-flow reconciliation

1. Save the exact rendered field labels, committed FormData values and selected approved-file hash before the normal submit click. Read office-specific work-authorization questions conditionally: when the label explicitly applies only to an office location and the candidate selects an offered Remote option, use a truthful not-applicable answer where the native field accepts it. Do not generalize this into permission to bypass an unconditional authorization question.
2. Observe the native candidate POST and correlate its request ID with the successful response, then save the normally reached applied page and exact employer acknowledgement email. A successful `/candidates` response and normal applied route form a stronger chain than either alone; do not navigate to a guessed confirmation route.
3. Evaluate post-submit visibility and success state rather than demanding that every input disappear from the DOM. Recruitee can retain empty application inputs after showing explicit successful submission; inspect their state alongside the correlated response and matching acknowledgement instead of resubmitting merely because fields remain in a snapshot.

## Exact email evidence normalization

1. Parse address headers with `email.utils.parseaddr` or `getaddresses` before comparing the mailbox to canon, because an acknowledgement can legitimately address `Candidate Name <candidate@example.com>`. Preserve the original header and require the exact intended mailbox; never replace an equality check with a loose substring match.
2. Scope copywriting QA to the candidate's actual outbound text. Keep employer acknowledgement wording unchanged, including its punctuation and signature, because third-party email formatting is evidence rather than candidate-authored copy.
3. If a read-only audit fails on header presentation or timestamp precision, repair the comparison and rerun the audit against the same provider and Teal identifiers. Never regenerate candidate text, resend an email or repeat an ATS application to repair the audit.
