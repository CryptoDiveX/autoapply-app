# Rippling public embeds and exact-role currentness

1. Preserve the exact employer-published `data-job-board-id` and inspect its observed public job-board script offline. When the published constructor defines `/embed/<boardId>/jobs`, fetch that read-only inventory to retain current titles, locations and exact detail links. Do not call candidate, application or tracking routes.
2. Compare every selected detail's current `__NEXT_DATA__` jobPost UUID, name, companyName and workLocations with discovery metadata. A cached title can describe a different region at the same UUID. Preserve both observations without repairing identifiers or inventing a second vacancy. Keep a Boston-only customer-success role separate from a current EMEA sales sibling. A sibling's Remote label does not establish worldwide hiring or candidate qualification.
3. For exact-role public GETs, preserve the final URL as well as HTTP status. A former detailed role can return HTTP200 after redirecting to the board with `rr_message=job_not_found`; that is exact-role not-found evidence, not a live application or employer-wide empty inventory. Save the current board's actual titles and locations separately. Do not silently substitute an APAC or country-restricted sibling or use a positive cached extraction to override the current redirect.
4. Inspect only candidate-facing metadata and public inventory. Keep employer HQ, legal identity, exact role hiring geography, application questions and live consent/challenge checks as separate gates. No public discovery establishes a submitted application.
