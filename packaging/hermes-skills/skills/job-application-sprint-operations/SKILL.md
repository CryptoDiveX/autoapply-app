# Job Application Sprint Operations

## When to Use

Use for Vasya's numeric application targets, all-night/continuous applying, source scouts, open-tab recovery, Applying-backlog cleanup and async result reconciliation.

This skill owns orchestration and counting. Load `vb-job-application-operator` for candidate canon, copywriting, document approval, exact form answers, ATS submission and detailed Teal/outreach procedures. Load `hermes-agent` before runtime configuration or troubleshooting.

## Standing Gates

1. Execute real applications, not just plans. Treat an emphatic instruction to keep applying as an execution request, not an invitation to repeat the setup summary or reset the existing target. Diagnose any stalled submission path, recover it safely and resume one real application owner before answering. Separate scheduled, launched, prepared, attempted, externally submitted and fully verified outcomes in every report; research-only ticks are not continued submitting. On repeated demands to apply now, read the latest completed tick's actual candidate-attempt and verified-submission counts before reassurance. If both are zero, say so directly and identify the bottleneck; do not substitute another enabled/running/all-night announcement for progress. Make a concrete execution or supply correction before replying, preserve an already-running sole owner, and never manufacture an application or bypass a safety gate to satisfy urgency.
2. In approved-document mode, use only the original approved PDF or a byte-identical renamed copy. Call `~/.hermes/profiles/vb-jobs/scripts/approved_resume_guard.py <exact-selected-file>` immediately inside every send/upload script with `subprocess.run(..., check=True)` and save its receipt. A repaired generator or worker visual PASS cannot approve a replacement. Do not execute legacy combined generator/senders or resend defective packages without explicit approval.
3. Use scoped `anthropic/claude-sonnet-5` for candidate copy and check it against imported canon/Q&A. Personalize cover text, exact screening answers and outreach without changing approved resume bytes. Reject unsupported named claims, incomplete/truncated copy, bad units and em dashes; never volunteer gaps unless a direct legal/form question requires them.
4. Enforce one direct employer per rolling thirty days across log, Teal, artifact folders, Sent and active work. Dedupe recruiters/aggregators by known end client, not their platform brand. Stop a second direct-employer role even if discovered after drafting.
5. Honor remote-only targeting and truthful Batumi residence. Canadian citizenship/authorization does not imply current Canadian residence or authorization elsewhere. EU visa-free entry is not permission to work.
6. During non-interference or document-incident recovery, use one submission/browser owner, at most three working pages and one Teal context. Scale with read-only public-source scouts, not additional browser owners. Scouts never send, drive CDP or write authenticated Teal.
7. Default to background Cloak without focus or Space changes. A request to open the browser authorizes that visible launch only, not later foreground automation; full overnight foreground use requires explicit authorization. Preserve the latest explicit browser-mode authorization across repairs and resumption instead of silently resetting to the default. Keep Vasya's installed CapSolver extension enabled and its configuration unchanged unless he explicitly requests a change. Distinguish preserving user-controlled development software from using it: do not invoke, outsource or rely on automated CAPTCHA solving for applications; leave challenged flows for the user and continue eligible alternatives without disabling his extension. Preserve a healthy browser and close only completed/dead owned tabs, not its persistent process or last user window. Do not turn an operator-authored healthy-browser no-restart precaution into a permanent prohibition on stopped-browser recovery. With continuing authorization and no current explicit stop or focus-hijacking restriction, pause future owner ticks, verify no live owner or matching dedicated profile process, use the documented headless-only recovery, verify actual flags and retained authentication, refresh target IDs and hand back to one owner. For authorized overnight work, preserve the tracked browser daemon across session release; never use this recovery to override a real user restriction. Use `references/cloak-browser-sprint-readiness.md` for the concrete launch recipe.
8. Prefer personalized LinkedIn notes; if the allowance is exhausted, Vasya authorizes sending without a note. Verify the exact profile's Pending/sent state, never duplicate Pending invitations or buy Premium. Email/WhatsApp/SMS require a current publicly published professional address/number, exact source evidence and a safe sending path. No guesses or private contact-broker data.
9. Count only external success plus exact Teal Applied/date/readable-note readback, approved-file receipt and claim/form/location QA. Upload storage success, a generic reachable thank-you route or a worker summary is insufficient. Match proof to the actual application channel: verify delivered attachment bytes for email applications, and the guarded upload plus normal submit/response/receipt chain for native ATS applications. Label unavailable remote attachment verification explicitly rather than claiming a downloaded hash. A bounced application email or application-quality incident revokes clean progress; a failed recruiter follow-up alone does not invalidate an independently verified ATS submission.
10. Use concise English, relevant emoji headers and numbered results. Keep routine overnight output and engine failures local unless updates are requested; never turn tool/config/error traces into user-facing progress. Determine delivery from the current message's origin, not from a worker's saved final response or its local-only policy. Internal completion notifications may remain local; a human request to process results, continue or explain an empty reply requires a visible answer with the independently verified total, remaining target, latest verified outcomes and actual owner state. Before ending that human-facing turn, check that the final response contains that answer, not empty text, `(empty)`, `[SILENT]` or a promise to report later, because tool execution and a worker's silence marker are not a response to Vasya.

## Daily throughput objectives

- Vasya's explicit operating target is100 job applications per day. Use America/Vancouver calendar days and actual provider/native submission times, not cumulative campaign totals, log-update times, launches or midnight target resets. Preserve the separate historical and100MORE ledgers; a daily overlay must not erase them or reapply to prior employers.
- Count verified applications to advertised named vacancies toward a jobs-per-day target. Report general/future talent intakes, profile-only interest, recruiter follow-ups, connection requests and research separately. A valid general application stays in history but must not be relabeled as an advertised vacancy to meet a quota.
- Read the full role before treating ATS employment metadata as a paid vacancy. A Worldwide, Remote, Part time job card can describe an unpaid voluntary community cohort and expressly disclaim any employment or internship relationship. Exclude such programs from application supply and job counts; a job-board Apply control does not authorize promotional-image permissions, unpaid assessment work or program participation.
- Use a cheap local mechanical daily checkpoint with explicit latest-lifecycle and evidence-reference checks, separate from fresh live-account audits. Track the real total, remaining target, eligible-role supply and shortfall. A counter, configured target or recurring job does not prove the rate is achieved; never guarantee100 independently of eligible supply and platform availability.
- Before claiming added research capacity works, exercise one real delegated call and verify its actual tool trace. If a direct-API delegation pin is credit-exhausted while the main provider is healthy, inspect profile-local routing against current Hermes documentation; use a backed-up documented inheritance correction when authorized, never purchase credits, expose secrets or claim a failed launch produced leads. Verify the repaired path before relaunching bounded public-only research.

## 1. Discover State and Freeze the Target

1. Honor the latest active request before historical backlog or out-of-order completions. Read the canonical log, current campaign manifest/ledger, live Cloak targets and relevant job/run state.
2. Treat an explicit fresh request for additional applications as a new target from the current verified baseline. For a continuation, preserve the existing target rather than silently resetting it. Announce scope when changing campaigns and retain old ledgers.
3. Save campaign start, baseline company set/evidence, additional target, computed numerical milestone, stop condition, timezone, owner/scout/report handles and evidence paths in a manifest. Use code for arithmetic and actual time for deadlines.
4. Label a historical log counter as such when old artifacts were not freshly audited. Maintain a separate ledger of verified new companies; a late old completion can change a global count without belonging to the new campaign. After an eligibility-policy change, distinguish inherited `verified_submitted` status rows from applications freshly checked against the current rules; a status-filtered total is not proof that every historical employer remains eligible. Report the numerical shortfall with that caveat rather than silently grandfathering old rows.
5. Snapshot existing open tabs. Process eligible unfinished targets through the single owner before fresh discovery; inspect confirmations before retrying or closing. Never take over another worker's live tab. Compare final targets with the initial snapshot and exact tick-owned target IDs rather than asserting that every remaining page must be the one Teal context. If unowned pages appear mid-tick, preserve them, stop new candidate actions and re-establish actual single-owner readiness before outbound; recover only local logging after a page-count assertion, never close unrelated tabs or replay submissions to make cleanup pass.

Use `scripts/recent_submitted_companies.py --company "Company Name"` for a cheap thirty-day guard, alongside the governing skill's other duplicate checks.

## 2. Launch Bounded Durable Work Immediately

1. List existing jobs and reuse/update an eligible recurring owner rather than accumulating duplicate schedules. Save a compact self-contained worker prompt in the campaign folder.
2. Include current canon/Q&A load order, approved-file gate, browser mode/ownership, remote/authorization facts, active platform exclusions, company/address no-retry lists, form QA, Teal completion, outreach and stop/report rules in the brief.
3. Keep the owner on small no-continuity ticks and scouts on separate read-only queues. For Vasya, use multiple platforms rather than concentrating the campaign on one board: rotate eligible Greenhouse, Lever, Ashby, Workable, Recruitee, SmartRecruiters, Breezy and direct employer careers flows. Use LinkedIn listings, Wellfound, Welcome to the Jungle and established remote boards for discovery when accessible, then follow the employer's prescribed application route. Record discovery source and actual submission platform separately, because several boards can point to the same employer and application. Diversify eligible alternatives, not duplicate submissions or forced platform quotas. Keep explicitly limited or defective channels paused; a request for multiple platforms does not clear their blockers.
4. Fire the owner and scouts now, not only at a future tick. For a paused job, resume it first, then request its immediate run; a successful tool envelope with executed=false or execution_skipped is not a launch. If the scheduler started the owner during resumption, preserve that execution rather than starting a competing worker. Keep returned async run handles and verify persisted schedules. Let async completion arrive normally; do not wait on or poll cron/delegated transcripts. Terminal CLI workers may instead be checked through their managed process status.
5. Distinguish an already-running skip from a new launch. After a successful launch returns a run handle, record it and end the dispatch step; do not fire the same owner again merely to produce activity or a visible reply. In single-owner mode, inspect live external state once if useful and do independent read-only research; never compete by filling a second tab. Pass the latest verified count and completed-company exclusions only when a new run actually needs launching.
6. Verify actual activity or outcomes before claiming applications are happening. A launch handle proves launched work, not an application. When checking continuation, inspect `hermes --profile vb-jobs cron list --all` and the relevant job's `Execution: running` field; `[active]` or a future next-run time establishes an enabled schedule, not a currently executing worker. Inspect owner and scout separately, then read the latest completed tick's actual submission count and dependency health. An enabled or executing worker can still be stuck in repeated research-only passes. If the same global dependency blocker recurs, resolve the permitted recovery path before describing submissions as continuing; if recovery is prohibited or needs human action, report that blocker plainly rather than hiding behind successful scheduler results. If the owner is already running, preserve it and report that fact without another run call. If no worker is active and the campaign is still authorized and before its deadline, start one safe bounded attempt before responding to a progress challenge. If the deadline has passed, answer that new submissions are stopped and distinguish any active recruiter correspondence from application work; a status question alone does not authorize extending the campaign. Ask once whether to resume, and define a renewed bounded scope only after authorization.
7. On a mid-run targeting or platform change, update both persisted owner/scout prompts and the shared worker handoff; use the durable notepad or a verified steering mechanism for in-flight work. Maintain one compact authoritative current brief rather than indefinitely stacking contradictory LATEST paragraphs. Update only the exact owner-authored latest-tick block after rereading the current brief under its established writer lock. Never replace a whole header-to-scope prefix: a parent can insert a new human-target or user-held-tab section there between reads. Preserve all unrelated sections byte-for-byte. If a broad prefix edit removes such a section, restore its exact text from the immutable before snapshot immediately and recover only the local handoff, never browser actions or sends. Preserve a backup of superseded instructions and all still-active safety gates, completed-target exclusions, finite follow-up requests and campaign objectives; a newer application-first priority must not silently cancel earlier follow-up work. Report the change as configured until a later readback establishes that the current worker adopted it. Preserve an already-running single owner instead of launching a competing browser worker. Pausing a schedule does not necessarily cancel its current run, and editing a prompt or skill does not rewrite that run's context. On a new employer/country exclusion or withdrawal instruction, pause affected future owner/scout ticks first, inspect in-flight execution separately and use a verified cancellation/steering mechanism when available. Persist the correction in the governing skill, campaign manifest, worker handoff and durable job notepad; `hermes --profile vb-jobs cron notepad <job-id> set user_stop <instruction>` records a cross-run notice, not proof that a live worker read it. Reconcile derived queues against the new exclusions before any authorized restart. Do not launch a replacement owner or claim work stopped merely because schedules were paused; verify execution state independently.

### Resume after a corrective pause

1. Treat a request to keep applying as clearing the temporary blanket pause only. Retain permanent employer/country exclusions, withdrawal protections, approved-document rules, the existing target and the original deadline unless the user explicitly changes them.
2. Verify that the old owner is no longer executing before handing candidate actions to a new run. Record the current tab snapshot and identify benign parent/user-owned settings or tracker pages in the handoff; those pages are not by themselves proof of a competing application worker. Preserve them and enumerate fresh target IDs instead of replaying historical tab assumptions. Reconcile the actual ledger with withdrawals and failures instead of copying stale status.json totals, because a summary can predate the correction.
3. Quarantine earlier queue entries that lack evidence for the new gate. Preserve append-only discovery and source artifacts; restore a prospect to eligible only after saving the required evidence. Do not silently treat old eligibility as current permission.
4. Clear or supersede temporary-stop text consistently in the manifest, worker handoff, stop notice and job notepad without erasing permanent restrictions. Publish one authoritative current handoff that identifies browser mode, ownership and which historical stop, path or target-ID assumptions are obsolete; contradictory older instructions can otherwise stop a healthy fresh run. Update affected persisted prompts before resumption. For a browser-only repair, leave an unaffected public-only scout running rather than pausing or duplicating it; update both jobs when targeting or safety policy actually affects both.
5. Preserve a healthy browser in its currently authorized mode; resuming applications does not require restarting the browser, changing its branding or reverting an explicitly authorized headed demonstration to headless. If the dedicated browser is stopped, use the recovery recipe in `references/cloak-browser-sprint-readiness.md` that matches the latest authorization. Background/headless remains the default without a foreground override, and continuation alone does not authorize new focus or Space changes.
6. Resume the existing schedules, fire bounded work, and verify actual execution state. Tell Vasya work has resumed and which safeguards remain; do not present the launch or an inherited ledger count as a newly verified application.
7. When the user explicitly renews continuous work after the old deadline, create an active continuation manifest and brief that supersede that deadline while preserving the closed run's history and original progress checkpoint. Update both persisted cron prompts and stale stop/platform notepad entries before resumption. Treat a null active deadline explicitly, never pass it into date parsing or run old deadline-stop scripts. A renewed continuous instruction must not be immediately canceled by an inherited morning-stop rule.
8. Remove a finite scout repeat cap when continuous work is authorized, then read back the persisted unlimited repeat and live execution separately. On installed runtimes where the CLI repeat argument is integer-only, do not assume it accepts the documented string forever; inspect normalization first. If confirmed that zero normalizes to unlimited, update through the cron tool with repeat0 and require persisted times:null. Never patch jobs.json directly.

For overnight manifest fields, practical cadence, bounded macOS idle-sleep prevention and a real morning-report job, use `references/overnight-parallel-application-sprints.md`. Do not promise a morning report without scheduling and reading back its actual job.

## 3. Complete Targets, Not Blocker Loops

1. Cheap-check live openness, eligibility, duplicate employer and obvious form/legal blockers before copywriting spend. Source scouts supply prospects, not final eligibility decisions. Compare a live employer-published compensation band with the current canon floor before drafting. Generic wording such as salary per company standards on another official page does not erase a specific live band for the same role. Preserve both sources, use a retrieved current exchange rate and programmatic annual/monthly conversion where needed, and defer below-floor roles without lowering expectations or spending on copy.
2. Give each tick a small batch and a real attempt budget. Continue to several alternatives after ordinary blockers rather than ending at the first failed target or browsing indefinitely. When the initial queue is exhausted, retain the existing campaign and verified total, exclude completed/dead/deferred targets, and consume newly appended scout rows or discover fresh official roles. Replenish through the existing read-only scout rather than restarting the campaign, recycling blockers or adding another browser owner. After repeated zero-ready batches, change the discovery hypothesis toward another canon-supported role family or genuinely new employer set; do not relax safety gates or reclassify research-only rows to fill a quota. While the sole owner is running and the scout recurrence is enabled, normally preserve the next scheduled scout instead of manually relaunching after every completion. An immediate refresh should have a concrete new supply hypothesis or newly available source, not merely another silence marker or unchanged blocker list.
3. Immediately archive/log dead or expired roles, close their tabs and add them to the campaign no-retry list. Dead roles are neither submissions nor human-action blockers.
3c. An absent exact Teal record does not establish a fresh target. Search local artifacts by the exact posting ID before reopening its form, including earlier lanes outside the active campaign. If a previous worker clicked Submit and recorded a visible challenge or uncertain result, preserve that attempt and inspect its saved proof instead of treating the current blank form as permission to replay. Repair a missing exact tracker separately, preserving same-employer siblings and keeping Applied date null when no submission was confirmed; tracker repair earns no application credit.
3b. Pre-filter newly discovered search results against local employer and exact posting lifecycle evidence before spending browser time. Apply that filter before repeat page extraction as well as CDP navigation: a fresh search result can repeat a known dead or specialist-gated role while omitting its saved disposition. Serialize the lifecycle decision before dependent extraction: do not batch exact-artifact discovery and a fetch of that same employer in parallel, because a late prior disposition cannot prevent an already-dispatched repeat fetch. Batch only independent discovery and already-cleared targets. Search target-specific artifact contents and original scout decisions, not only canonical headings, broad inventory matches or artifact filenames, then bind each fetch or inspection to the resulting exact allowed set. Search every shared queue bucket, including `country_verified_research_only`, `research_only` and deferred nested rows, by the exact observed posting ID as well as source URL before any copywriting spend. Include the historical parent campaign queue named by the continuation manifest: an employer absent from the active continuation can still be quarantined under the parent's `country_verification_required`. Resolve the observed official domain rather than assuming a `.com` suffix, and inspect newly discovered parent dispositions before any dependent fetch; recover late matches with local evidence only. A missing canonical-log heading, absent Teal record or new embed/application query does not make a previously research-only posting fresh or clear its geography gate. Read its original disposition and require genuinely new eligibility evidence before promoting it. Match the exact source URL and all current Teal stages, including Archived; when the full inventory projection omits `note`, fetch the exact matching record's `attributes.note` before reopening its form. A title absent from canonical section headings does not make that source fresh, because earlier multi-company preflight sections can already contain its exact dead status or unresolved questions. Bind each browser-inspection dispatch to the retained allowed set produced by exact employer/posting lifecycle prefiltering. Printing a dead, deferred or completed match is not enforcement if an unconditional inspect call still executes afterward; assert that the exact URL is allowed immediately before opening it, and recover only logging if an accidental read-only repeat occurs. Resolve actual company aliases and exact source URLs rather than treating a page-wide substring as an employer match: `Persona` can match `personalized`, `Pliant` can match `compliant`, and a vendor mentioned as a tool is not the hiring employer. For brands ending in punctuation, such as `Aha!`, do not wrap the entire literal in two word boundaries: a boundary after the final nonword character can miss the exact brand. Match the actual alphanumeric core with appropriate token boundaries and retain the observed punctuated display alias, then check the exact employer domain and every queue object before dispatching extraction. A negative brand-only novelty screen is provisional until that domain/source check passes; recover a late prior disposition with local evidence only, not another native inspection. Apply token boundaries to short plain-text employer aliases before classifying a lifecycle match, then inspect the exact containing record or section. Inspect borrowed prefilter helpers before reuse: a legacy re.escape substring implementation can match Ably inside demonstrably or immutably despite this rule. Reject those false attributions with an exact-word local check and a supported word-boundary/domain search before dispatch; search_files does not support lookaround syntax. Preserve the failed read-only projection and recover only filtering, never outbound actions. Preserve the rejected substring hit and rerun only the read-only prefilter; never treat an unrelated compliance sentence as a prior employer application or silently clear a genuine exact posting match. An earlier exact deferral should be reopened only for a genuinely changed route or requirement, not because a fresh search repeats the stale mirror.
3a. Reconcile the derived next-target queue after every completed tick against the verified ledger, employer/end-client aliases, exact completed posting URLs and exact deferred/dead application URLs. Inspect each queue field's current row type before merging exclusions: a skip list can contain full lifecycle dictionaries rather than company-name strings, so deduplicate dictionaries by observed identity instead of calling set on mixed rows. A queue-only verifier failure must be repaired from the saved exact lifecycle row without repeating a ledger append, send or Teal mutation. Resolve queue metadata edits by exact JSON object path and nesting depth, not the first textual occurrence of a key: nested scout summaries can repeat top-level keys such as next_supply_hypothesis. For a large shared queue requiring targeted file-tool patches, hold the established scout/file locks, parse the entire current JSON locally, locate each root-key span at its verified serialization depth, decode its complete value with JSONDecoder.raw_decode and assert it equals that root object's value before patching. Require one unique exact span, preserve a before snapshot, then parse and compare the final whole object and unchanged scout fields. After a file-tool patch that atomically replaces the queue, keep the shared directory locks held and reopen the current pathname for each later read and final verification. A pre-patch file descriptor can still point to the old inode and falsely report a stale queue; recover only the read-only verifier, not the already-completed patch, tracker or outbound action. This avoids both nested-key misattribution and stale whole-file replacement; recover only queue metadata if a patch fails. Preserve the exact current field and its source before patching, verify the intended object afterward, and recover only queue metadata if attribution or nesting was wrong. Remove stale completed or deferred rows even when their display company differs, while preserving the scout's append-only prospects and all saved blocker evidence. When a scout updates the derived queue during owner reconciliation, reread the current queue and recover only the owner-owned exact top-level fields and completed-employer removals with targeted patches. Preserve the scout's newer research rows, source and supply hypothesis; a refused or stale whole-file write is a queue-only recovery, never permission to replay the verified ledger append, tracker mutation or outbound action. Before modifying a shared queue, inspect the current scout writer's actual locks and acquire those same directory locks plus its file-level flock in the same order, then reread and update only owner-owned exact top-level fields. A separate owner-only lock does not serialize the scout and can silently discard fresh prospects even when the write itself succeeds. Keep completed recruiter-client pairs excluded by known client or exact posting URL, not by blanket recruiter-brand exclusion. A row's presence in an old eligible array does not override a newer completion or deferral.
4. Preserve reusable approved files, target-specific answers and form evidence when a blocker appears after preparation. Reuse those after revalidation instead of regenerating copy. Name target helpers distinctly, such as company-copy-r1.py, not copy.py, email.py or other Python standard-library module names; local shadowing can recursively execute candidate-copy code during ordinary dependency imports. Rename a shadowing helper and rerun only the failed preparation step, never an outbound sender. After an interrupted combined preparation/sender, inspect exact Sent plus saved send intent/result before any recovery. An existing renamed PDF, passing guard test or acquired lock is preparation evidence, not a send. If immutable-file assertions now prevent rerunning preparation, preserve those files and isolate only the genuinely unexecuted sending step after fresh eligibility, duplicate and Teal preflight; never delete provenance or relax assertions merely to rerun the whole sender.
4a. Assert immutable evidence paths are unused before CDP target creation, and put receipt creation inside the target cleanup try/finally. Otherwise an existing filename can raise after opening a page but before cleanup is armed. Preserve original artifacts and recover only missing readback or exact owned-tab cleanup under a new prefix, never replay candidate or sending actions. If a snapshot helper prints a character-truncated JSON string, parse its complete saved JSON artifact for projections rather than parsing the truncated console text. A projection failure after the snapshot was saved is read-only evidence recovery, not a reason to reopen the page or rerun the preflight.
5. Before submit, read exact visible values and normalized hidden payload. Check location autocomplete, field-label alignment, requested units/currency period, files, legal facts and named claims. On Ashby, inspect current rather than stale React state; on Lever, allow upload parsing to settle before typing fields it can overwrite. For repeated careers-card actions, bind the smallest visible ancestor containing the exact selected role and only its own button. A broad parent can select another role silently. Require the resulting observed URL and heading to match before candidate entry or copywriting; recover a wrong read-only selection without repeating any outbound action. Keep older Eastern-hours roles separate from newly published global-flexible roles at that employer, and evaluate each exact role independently.
6. Stop for passwords, 2FA, payment, permission prompts, visible CAPTCHA, required identity documents and unsupported legal/eligibility claims. Save the human-action blocker and pursue another eligible target, never bypass or invent an answer. Explicitly approved routine data/privacy consent is not a license for unrelated legal claims.
7. Recover uncertain submissions by inspecting the original target, confirmation/email and saved evidence first. Never resubmit merely because CDP disconnected. Require success reached through the normal flow, not a guessed confirmation URL.
8. Complete exact Teal readback and evidence logging before ledger entry. If Teal alone fails after external success, queue idempotent logging repair and do not resend the application.
9. Perform bounded follow-up for each verified application and save sent, blocked and queued channels separately. Do not send redundant immediate follow-up to the same inbox already used for the application. Recheck bounces each tick and never retry failed addresses.

### Diagnose low throughput before adding workers

- Persist the sole owner's broad-search batch count before dispatch, not only the scout's. Assert that the counter write or patch succeeded before dispatching dependent searches. If a file tool refuses an overwrite, read the current counter and recover only that local update; never continue the search loop on the failed write. Keep one tick-wide counter across changes of role family, language or geography. After three zero-ready broad batches, enforce the stop before the next tool call and use only already-observed native inventories, exact employer-specific recovery or local shortfall logging. A changed query theme does not reset the cap. If a read-only excess occurs, preserve its actual count and recover only evidence and handoff; never invent a candidate attempt to compensate.
- Measure completed ticks, zero-verified ticks, public preflights, actual candidate attempts and strict completions separately. After consecutive zero-attempt ticks, classify the bottleneck before changing cadence: no active owner, failed shared dependency, stale/duplicate supply, real eligibility/consent blockers, or excessive administrative work. Start an idle authorized owner immediately; recover a shared dependency only through its safe documented path; change the employer/source/role-family hypothesis for exhausted supply; defer genuine blockers; and return administrative work to its bounded queue. Shortening the schedule, adding another priority paragraph or launching another research pass alone is not a demonstrated throughput repair. Verify later candidate actions and submission outcomes before claiming improvement.
- Keep application attempts first while preserving actionable recruiter replies. Batch low-priority multi-year-old follow-up reviews separately with a small budget and retained cursor; do not spend five history reads and tracker rewrites every application tick on stale rows. Never cancel the user's finite full-pipeline follow-up request or mark those pending rows completed merely to improve application counts.
- Service accepted-connection monitoring at its actual twelve-hour due queue, not by rereading the same Pending profiles every application tick. A fresh direct request makes a new check due now even when the last partial scan was within twelve hours. Advance unresolved tracked contacts and the saved coverage cursor in a bounded pass, then return to applications; neither a pending request nor repeated scans of the same newest cards proves the requested follow-up was performed. Preserve genuine new acceptance and incoming-message work without using repeated unchanged profile checks as application progress.
- Distinguish welcoming language from an exclusive residence requirement. A role saying remote applications based in North America are welcome establishes that accepted scope, not an explicit worldwide policy or a proven ban on every other location. Keep Batumi eligibility unresolved until affirmative scope is established, preserve separate mandatory working-hours requirements, and never rewrite welcome as must be based when logging a deferral. This prevents overstating geography evidence without relaxing strict remote targeting.
- Distinguish an experience preference from a hard eligibility attestation. A small near-match year gap alone need not exclude canon-supported work when an honest answer is possible; never invent tenure or override actual legal, location, credential, specialist-experience or consent requirements. Retain the exact posting and form wording rather than assuming every desired qualification is a disqualifying checkbox.
- Log scout-only dead or plainly ineligible public discoveries locally when no candidate work or existing target repair is involved. Do not create hypothetical Teal vacancy records merely to document that an employer inventory has no matching role. Materially prepared, entered, submitted, uncertain and user-requested targets still require exact tracker handling and full proof.
- Keep all-artifact lifecycle discovery bounded: first filter the current full Teal inventory, canonical log and every queue bucket, then use exact employer-domain or posting-ID file searches and inspect the containing records. Do not recursively read every historical JSON snapshot once per candidate alias; duplicated multi-megabyte inventories can exhaust a tick before any application attempt. If a broad scan times out, recover only the narrow read-only prefilter and preserve all outbound uncertainty protections.
- Reuse one current full inventory for within-tick discovery/dedupe and exact target reads before writes and verification. Cache unchanged already-correlated failure evidence while still searching for new or changed bounces at normal checkpoints. Consolidate mechanical verification without deleting safety gates or confusing cached proof with current delivery guarantees.
- Request concise complete Sonnet copy once and reject genuine claim, contact, legal or user-format defects. Do not burn repeated revisions solely on arbitrary operator-imposed literal phrases or cosmetic word counts when the actual user requirements are satisfied.
